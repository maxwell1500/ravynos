THE BLOCKER
---------------------------------------------------------------------------------
Load closure. libsystem_c.dylib LINKS but cannot LOAD: of its 272 undefined
symbols, 139 are resolvable against installed dylibs and 133 are not. 126 of
those 133 come from libsystem_kernel, which is an 8,064-byte stub.

libsystem_kernel is blocked TWICE over.

(1) ITS SYSCALL HALF — 454 stubs generate cleanly, but cannot be assembled.

    Inputs are correct and complete:
        Kernel/xnu/bsd/kern/syscalls.master            58,794 B  present
        Kernel/xnu/libsyscall/xcodescripts/create-syscalls.pl
        Kernel/xnu/libsyscall/xcodescripts/compile-syscalls.pl
    create-syscalls.pl produces 454 .s files, stubs.list, and SYS.h (16,519 B).
    compile-syscalls.pl then fails on EVERY stub, identically:

        ___accept.s:9:354: error: invalid instruction mnemonic 'unwind_epilogue'

    THE KEY FACT, AND WHY IT MATTERS: the string "unwind_epilogue" appears in
    NO file in this project. It is absent from Kernel/xnu/libsyscall/, from the
    generated sys/ tree (including the emitted SYS.h), and from Kernel/xnu/bsd/.
    Repo-wide count: 0. Yet the assembler reports it at a specific line and
    column. The assembler is therefore being handed text that does not exist
    in any file on disk.

    Reproducing command (from syscalltest/clean/):
        xcrun clang -arch x86_64 -c -isysroot$SDK -I$SDK/usr/include \
            -I$T/sys ___accept.s -o out.o
        -> rc=1, no object, the error above.

    Already tried and ruled out, so they are not retried:
      - stale artefacts: reproduces in a pristine empty directory
      - stray header on the include path: persists under -nostdinc -nostdinc++
      - preprocessor not running on lowercase .s: persists with
        -x assembler-with-cpp
      - wrong assembler path: clang -v shows the integrated assembler
        (clang -cc1 21.0.0, x86_64-apple-macosx26.0.0), and -fno-integrated-as
        gives the same error
      - preprocessed output: unwind_epilogue is NOT in the -E output either
        (0 occurrences), and the -E file is not line-aligned with the source,
        which is why a line:column from the assembler cannot be looked up in it

    Declaration-not-header, because the in-tree headers carry #if KERNEL
    material that must not reach userspace. Verified 0 errors.

    What remains is NOT a missing type. The failing TU is
        obj/mach_vmUser.c:8 -> internal_hdr/include/mach/mach_vm_internal.h:137

NEXT STEP, IN ONE COMMAND
---------------------------------------------------------------------------------
Read what the assembler is actually consuming. The error names a line and
column of a buffer that contains none of the project's text, so the useful
question is not "which file emits it" but "what does clang hand the assembler
for a lowercase .s on this host". Concretely:

    xcrun clang -arch x86_64 -### -c -isysroot$SDK -I$SDK/usr/include \
        -I$T/sys ___accept.s

That prints the full driver pipeline including the exact assembler input path,
which distinguishes "clang is invoking something that substitutes content" from
"the source really does contain it somewhere unsearched". Do not re-run the
five ruled-out probes above.

An alternative worth weighing before more debugging: the .defs-based mach header
generation, and the syscall stub assembly, both smell like a HOST TOOLCHAIN
mismatch -- xnu-11215 stubs assembled by clang 21 on macOS 26. If that is the
cause, no edit inside this repo will fix it and the answer is a toolchain that
matches the target. That is a hypothesis, not a finding.

THE LESSON, WHICH IS THE MOST VALUABLE OUTPUT OF THIS SESSION
---------------------------------------------------------------------------------
Most of the stalls in this project were MODE problems, not content problems.
The source was correct and the INVOCATION was wrong -- five separate times.
Twice, the confident answer pointed at the source when the fault was in how the
tool was being called.

Supporting rules, all learned the hard way here:
  - Read what the tool produced, not what you intended to produce. When a tool
    reports a line and column, establish which artefact that numbering refers
    to before grepping anything: -E output and -c input are not line-aligned.
  - Never treat "no match" as "no data". A grep returning zero is "no match",
    not proof of absence. Here the assembler and the grep contradicted each
    other, and the assembler was closer to the truth.
  - Check that the instrument can fail the way you need it to fail, before
    trusting it to pass. A C preprocessor was used to test a mig grammar
    question; it would have reported success on a statement it does not parse.
  - Verify the inputs a tool will actually use, including supporting headers,
    not just the ones you counted. stubs.list had 456 lines and SYS.h was
    never checked.
  - A hypothesis that is half right is the most dangerous kind, because the
    half that is right lends false confidence to the half that is wrong.
  - When two observations conflict, do not settle on the most plausible one.
    Carry it as a hypothesis and go get the measurement that decides it.
  - A derived list only beats a hard-coded one if the derivation is right; a
    wrong derivation is worse than an honest list, because it reports with
    confidence.
  - Never interpret output from a process that has not exited.
  - A gate earns the right to be committed by demonstrating a clean run, not by
    being written. The derived gate here has produced false reds and is
    correct on a full run, but its NEGATIVE direction is still unverified --
    treat a red from it as "investigate the gate first".
